# 1\. 持久化

# 一\. 认识持久化

我们之前学过的mysql的事务，有四个比较核心的特性

1. 原子性

2. 一致性

3. 持久性（和持久化说的就是一回事）

4. 隔离性

把数据存储在硬盘上 \-\> 持久

把数据存储在内存上 \-\> 不持久

重启进程/重启主机 之后，数据是否存在

Redis 是一个内存 数据库，把数据库存储在内存中的

内存中的数据是不持久的，要想能够做到持久，就需要让 redis 把数据存储在硬盘上

Redis 相比于 MYSQL 这样的关系型数据库，最明显的特点或者说是优势就是效率高，快

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MzA1ODNhNTlhNTRlNTZlZTIyNGQxYTM0Y2EyZTgxYzVfYzg2NjJkZmIzMTY5YWQ5YWRiNmI5MzdiOWQxYTNmYTJfSUQ6NzY2NzAzODYyMzMzODI4NjAwOV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

为了保存速度快，数据肯定还是得在内存中，但是为了持久，数据还是得想办法存储在硬盘上

Redis 决定，内存中也存数据，硬盘上也存数据

这样的两份数据，理论上是完全相同的，实际上可能存在一个小的概率有差异，取决于我们具体怎么进行持久化

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MDNmMmE4OTM0YzBiMDI0NGQ4NTZkMDI1N2YyNjRhY2JfNWI5Yzc5MTU3OTNmNWZhMDMyZmY1ZDI3MzkwOTI5Y2VfSUQ6NzY2NzAzOTI1NzY1OTM5NTA0MF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

代价就是消耗了更多的空间，同一份数据，存储了两遍，但是毕竟硬盘比较便宜，这样的开销不会带来太多的成本

# 二\. RDB

## 2\.1 RDB 的触发时机

RDB 定期的把我们 Redis 内存中的所有数据，都给写入硬盘中，生成一个 “快照”

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YmNhMTU1ZjIxZDVkMzJjZDk5M2RhOTU3Zjc1MjEzY2VfMjIzMmViNzQ2ZTQ3MGM4MzRkY2E2NTYxYTRmNDQ3NGZfSUQ6NzY2NzA0MzYxNzA4MTE2NzEzNF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

“定期” 具体来说，又有两种方式

1. 手动触发

程序员通过 redis 客户端，执行特定的命令，来触发快照生成 save bgsave

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MTNhZDcxODdjNmFkOWQ0OTFhMDVmN2FhMzVhOTcxMjRfNGViYjVjOGEwMTZmZTU1YzRlNjgyNWIyZmVhYWY2YTlfSUQ6NzY2NzA0NTEzMjIzNTg2OTE1N18xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

2. 自动触发

在 redis 配置文件中，设置一下，让 redis 每隔多长时间/每产生多少次修改 就触发



## 2\.2 RDB 的 bgsave 执行流程

这里并发编程是使用的多进程，不是多线程

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=OTM1Yzg2YjRjN2MzOGE0M2YwOGY5Y2E3MWQ4ZmVmNjdfNWFiN2RkODc2ZjcxNDE0Nzk0MGJjMjA1MWE0OTM1ZTZfSUQ6NzY2NzA3ODQ1Mjg4MTYwNzY0OF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

1. 判定当前是否存在其他正在工作的子进程

比如新增已经有一个子进程正在执行 bgsave，此时就直接把当前的 bgsave 返回

2. 如果没有其他的工作子进程，就通过 fork 这样的系统调用，创建出一个子进程来

fork 是 linux 系统提供的一个创建子进程的 api（系统调用），如果是其他系统，比如 windows，创建子进程就不是 fork（CreateProcess\.\.\.\.\.\.\.）

fork 创建子进程，简单粗暴，直接把当前的进程（父进程）复制一份，作为子进程

一旦复制完成了，父子进程就是两个独立的进程，就各自执行各自的了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MGFjMGM5OWFkZmExMWMyOTM3MzhhMmYxMTljNWEwMjhfM2YyZTE2N2QwNjdjNWJhMTA2OGY1YTMyOTM5YmM5NGNfSUQ6NzY2NzA3OTgwMzQ4NjI2MDE4MF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

因此，复制出来的这个 “克隆体”（子进程）的内存中的数据就是和 “本体”（父进程）是一样的

接下来安排子进程去执行 “持久化” 操作，也就相当于把父进程本体这里的内存数据给持久化了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=OTVkMDg2NDJjYTFiNGMxZjhiMjlmNjE0ODE3ZmYwYmRfMjhiY2IzMTQyNWQ4MmNkOTZlOGFlZWVjYTM1M2VhY2RfSUQ6NzY2NzA4MjQxOTA1MjcyNzU2Ml8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

此处的性能开销其实挺小的，fork 在进程内存拷贝的时候，不是简单无脑的直接把所有的数据都拷贝一遍，而是 “写时拷贝” 的机制来完成的

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjgzYjIxNmY4NTE3NGU2NjhjMWY0NGQ1YmQzZTQzMDBfMDAzODdiODliNGRkMWNiM2FjZmMxMTY1NmU4NGFhMjVfSUQ6NzY2NzA4MzQ4NjI0NTAxNDUxNV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MDM2MTc1OTcxMWRiZDYzYTY4MjA2MWE4YTlhZTYyYTdfMzZiN2E0M2U5ODQzMzg1OGQ5ZmQ1MDdlNWJhOTQ2YzZfSUQ6NzY2NzA4Mzc2NzY3MjA5ODA4M18xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

如果父进程这里产生了修改

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MzY4MDUwYjAzZmQyYjhjMGY4NjkzNTdlYzZhMWZhMTFfZjkzMjMwZTkwMmUzYTIzMDE5ZjNlNGFlZGVhNWI4MDdfSUQ6NzY2NzEwOTI4NTcxNDAwNDk2Ml8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

写时拷贝的整体思路，类似于 “懒汉模式”

在进行 bgsave 这个场景中，绝大部分的内存数据是不需要改变的，整体来说这个过程执行的还挺快的，这个短时间内，父进程中不会有大批的内存数据的变化

因此，子进程的 “写时拷贝” 并不会触发很多次，也就保证了整体的 “拷贝时间” 是可控的，高效的

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NWMwZGQyZThhNTAyNDM0NWQzMjhkMzc3MDdmZTc3YWNfZjFhNTNiZDg1NmEzYzYwMzNjOWZjNGNiMzY4ZGUxNDRfSUQ6NzY2NzExMDA3NDE4Mzc5ODA0NV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

3. 子进程负责进行 写文件，生成快照的过程，父进程继续接收客户端的请求，继续正常提供服务

4. 子进程完成整体的持久化过程之后，就会通知父进程，干完了，父进程就会更新一些统计信息，子进程就可以结束销毁了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YmI4NTc4OGI4ZGM4MzFmYTI5MjY3OGMxMjY2OGFkNzRfMTc0NGFiNmJhN2U1YWI4NDcxYmY0OTkwYzI1NjRmYTFfSUQ6NzY2NzExMDg2MDA5MzEzMTk4M18xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

## 3\.2 AOF 是否会影响到 redis 性能

redis 虽然是一个单线程的服务器，但是速度很快，为啥速度快，重要原因是因为只是操作内存，引入 AOF 之后，又要写内存，又要写硬盘，还能和之前一样快了嘛？

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=M2I2OWJmZjcyMTdiYmI3M2UxNTNmOTMxNGI4ZjE0OTBfZTA4YTVlMzg1YWZhMTAyODhkYjUxNGU4Yjk1YTcxMGVfSUQ6NzY2NzQwOTAyNDI4NDA4NTE5MF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

实际上，是没有影响的，并没有影响到 redis 处理请求的速度

1. AOF 机制并非是直接让工作线程把数据写入硬盘，而是先写入一个内存中的缓冲区，积累一波之后，再统一写入硬盘

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ODdhZDcyMTVhMDkyZTIyMTAzZjIyYjk4OWEwN2EwMzNfYjhmY2M4ODAwYzE5Njg0MDUwOGQ3ZTU4ZTQ4YmM0OTRfSUQ6NzY2NzQwOTQxNjY4OTgxNDUxNV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

2. 硬盘上读写数据，顺序读写速度是比较快的\(但是还是比内存要慢很多的\)，随机访问则速度是比较慢的

AOF 是每次把新的操作写入到原有文件的末尾，属于 顺序写入

## 3\.4 AOF 的重写机制

AOF 文件持久增长，体积越来越大

会影响到 redis 下次启动的时间，redis 启动的时候要读取 aof 文件的内容

注意，上述 aof 文件，有一些内容是冗余的

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MTRlNWE3N2ZlY2E5ZWQxNzA0NThmMjg5ZWE4OTQ0N2NfZmU0NmEwN2ExYmEyOTQ5NDNmMjhkNThkNjc3NGRlMDJfSUQ6NzY2NzQ2MjY5ODY3ODM1NjkyOF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

aof 文件记录了中间的过程，但是实际上redis在重新启动的时候，只是关注最终结果

因此 redis 就存在一个机制，能够针对 aof 文件进行整理操作，这个整理就是能够剔除其中的冗余操作，达到给 aof 文件瘦身这样的效果

这就是重写机制

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MjFkYWQzOTRmZjVlZGRlZjMyZDZjMjY1NjNjZmJmYWZfMTdjOGM1MTUwZTlhMzI2MWZlNmJjNzkwOGRlNDJiMzFfSUQ6NzY2NzQ2NDIxOTU5MTgyMjYwMV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

**AOF 重写的流程**

跟 rdb 类似，会创建子进程，父进程仍然负责接收请求，子进程负责针对 aof 文件进行重写

注意，重写的时候，不关心 aof 文件中原来都有啥，只是关心内存中最终的数据状态

子进程只需要把当前内存中当前的数据，获取出来，以 AOF 文件的格式，写入到一个新的 AOF 文件中（内存中数据的状态，就已经相当于是吧 AOF 文件结果整理后的模样了）

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZWQ4ZWFlZDEyNDFlNTc2OGI0NmM5NzVlZDcyYTA2YzNfNDNjYjQ1OTQ1ZGZjNTdlZmFlMTQ5MGI0ZDU0M2Y4NzhfSUQ6NzY2NzQ2NTczMTk5NDczMzgwNF8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

此处子进程写数据的过程，非常类似于 RDB 生成一个镜像快照

只不过 RDB 这里是按照二进制的方式来生成的

AOF 重写，则是按照 AOF 这里要求的文本格式来生成的

都是为了把当前内存中的所有数据状态记录到文件中！

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NTg0YzQzMWI4YmFmY2Y1ODI3Mjg0ZmVhYTA4OWJhYmFfODc0NDQ4NDBiZTkxNzA4NWNiYmIwMjU4MWM5MWZmZTBfSUQ6NzY2NzQ2NjE4OTg5MTQ1NTk2Nl8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

子进程写新 aof 文件的同时，父进程仍然在不停的接收客户端的新的请求，父进行还是会把这些请求产生的 AOF 数据先写图到缓冲区，再刷新到原有的 AOF 文件里

在创建子进程的一瞬间，子进程就继承了当前父进程的内存状态，因此，子进程里的内存数据是父进程 fork 之前的状态，fork 之后，新来的请求，对内存造成的修改，是子进程不知道的

此时，我们在父进程这里又准备了一个 aof\_rewrite\_buf 缓冲区，专门放 fork 之后收到的数据

子进程这边，把 aof 数据写完之后，会通过信号通知父进程，父进程再把 aof\_rewrite\_buf 缓冲区中的内容也写入到 新 AOF 文件里

就可以用新的 AOF 文件代替旧的 AOF 文件了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YWRlMjY4ZWIxZmRmNzgxZTdlNTljNmExYjVlMWU0MmFfMjhjN2RlNjZiNzAwMDc5OTg1ZGYwMDEzNjA1OTQ4YThfSUQ6NzY2NzQ2Nzg0OTU5NDE2MjEyM18xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MDA0ODliNjE3Njg0YmI0NzQ5OTE1MDg3NWQ0NjVlODRfODc0NDA2NzEzZTVjYjM3Yjc4NjVmYjg5MGI3OGQ2ZTlfSUQ6NzY2NzQ3NTMwNDM0MDE0NzE3NV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

如果在执行 bgrewriteaof 的时候，当前 redis 已经正在进行 aof 重写了，此时不会再次执行 aof 重写，直接返回了

如果在执行 bgrewriteaof 的时候，发现当前 redis 在生成 rdb 文件的快照，会咋样呢，此时 aof 重写操作就会等待，等待 rdb 快照生成完毕之后，再次执行 aof 重写

rdb\- 对于 fork 之后的新数据，就置之不理了，aof 则对于 fork 之后的新数据，采取了 aof\_rewrite\_buf 缓冲区的方式来处理

**rdb 本身的设计理念，就是用来 “定期备份” 的，只要是定期备份就难以和最新的数据保持一致**

**aof 的理念则是实时备份**

实时备份不一定就比定期备份更好，还是看实际场景的

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZGZlMzRiZDE1NmZhNGYxYmVkODg1YmUyNDIzMmUyYTRfMGUwMmQ1ZDhjOTNiMDIzMTE0NGY3ZGUwMzI3MGMwMGJfSUQ6NzY2NzQ3NjU3ODkxMzgxNTg0MV8xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

现在的系统中，系统的资源一般都是比较充裕的，aof 的开销也不算事，一般来说，aof 的适用场景还是更多一点的

父进程 fork 完毕之后，就已经让子进程写新的 aof 文件了，并且随着时间的推移，子进程很快就写完了新的文件，要让新的 aof 文件代替旧的，父进程此时还在继续写这个即将消亡的旧的 aof 文件是否还有意义【不能不写】

考虑到极端情况，假设在重写过程中，重写了一半了，服务器挂了，子进程内存的数据就会丢失，新的 aof 文件内容还不完整

所以如果父进程不坚持写旧 aof 文件，重启就没法保证数据的完整性了

# 四\. 混合持久化 \&\& 对于信号的解释

## 4\.2 对于信号的解释

当 redis 上同时存在 aof 文件和 rdb 快照的时候，此时以 aof 为主，rdb 就直接被忽略了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YWE3ZTAwNjA1NjkxYTRjNmQ1NzdmZmYyMGQ0NTViODZfZjEwYzljNjVhNjBiNTg3ZTY3Y2JlNmE1OTY2Y2UyY2ZfSUQ6NzY2NzQ4ODQ5MjUxMTIwMjI3M18xNzg1MjI2NzQ3OjE3ODUzMTMxNDdfVjM)

**因为 AOF 中包含的数据比 RDB 更全**



之前AOF和RDB流程的时候，都有一个信号通知父进程的步骤

信号这个东西，可以认为是 Linux 的神经系统

信号可以说是进程之间的相互作用（也可以视为是进程间通信的一种手段）

信号能表达的信息有限，并非像 socket 这样的发那是可以传输任意的数据

因此，像上述 父子进程 场景中，子进程表达 “我干完了” 这种简单的信息传递，使用信号也是 OK（当然使用其他的进程间通信方式也可以）
