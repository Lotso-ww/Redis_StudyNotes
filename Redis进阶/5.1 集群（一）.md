## 2\.1 哈希求余

哈希求余 \-\- 借鉴了哈希表的基本思想，借助 hash 函数，把一个 key 映射到整数，再针对数组的长度求余，就可以得到一个数组下标

比如有三个分片，编号 0 1 2，此时就可以针对要插入的数据的 key（redis 都是键值对结构的数据）计算 hash值（比如，使用 md5）再把这个 hash 值余上分片个数，就得到了一个下标，此时就可以把这个数据放到该下标对应的分片中了

md5 本身就是一个计算 hash 值的算法，针对一个字符串，里面的内容进行一系列的数学变换 \-\> 整数

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YjQ3ODY2YmQ0OWRmYzhlYjg0OTJjYWZjNGJhYTgzZDBfNjU2Nzc0MzJmZjc3NzJjMTAzYzQwNjFjZGJhNDZkMzBfSUQ6NzY3MDgyMzY3MTE1ODAzMzMzN18xNzg3MDE0OTQ3OjE3ODcxMDEzNDdfVjM)

MD5 是一个非常广泛使用的 hash算法

特点：

- md5 计算结果是定长的，无论输入的原字符串多长，最终算出的结果都是固定长度

- md5 计算结果是分散的【所以可以作为哈希函数】，两个原字符串，哪怕大部分都相同，只有一个小的地方不同，算出来的 md5 值也会差别很大

- md5 计算结果是不可逆的【所以可以用于加密】，给你原字符串，可以很容易算出 md5 的值，给你 md5 的值，很难还原出原始的字符串的（理论上是不可行的，计算量太大了）

网上的一些 md5 破解，其实是把一些常见的字符串的 md5 值，提前算好，保存下来，就按照打表的方式，根据 md5 值映射到原字符串，能不能查到，就随缘了



一旦服务器集群需要扩容，就需要更高的成本了，分片主要目的是为了能提高存储能力，分片越多，能存的数据就越多，成本也就更高

一般都是先少搞几个分片（3个），但是随着业务逐渐增长，数据变多了，3 个分片就已经不足以保存了，所以我们要 “扩容”，引入新的分片，N 就改变了，当 hash 函数和 key 都不变的情况下，如果 N 改变了，整体的分片结果仍然会变

如果发现某个数据，在扩容之后，不应该待在当前的分片中了，就需要重新进行分配（搬运数据）

此处列出的这些值，就可以脑补成 hash\(key\) 假设当前计算完 hash值 之后，得到的数值正好是 100\-120

## 2\.3 哈希槽分区算法

哈希槽分区算法，是当前 redis 真正采用的分片算法，之前讲的两个方法都没被 redis 真正采用而是使用的这个

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzU4YTQwNmI2MGRlOTMwNTEwNDRlYzcyODk5OTBlZmRfZTlmYjc2ZDM2ODExYmRjYzJjMjg2MTgxYzQ4ZWM1ZjJfSUQ6NzY3MTEyODc0MDQyNDQzNjk1MV8xNzg3MDE0OTQ4OjE3ODcxMDEzNDhfVjM)

16384 其实就是 16 \* 1024 \-\> 2 ^ 14（16k）

hash\_slot：哈希槽

会进一步的把上述的这些哈希槽，分配到不同的分片上

假设有三个分片，有一种可能的分配方式

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZGNhZTA4ZjU2NzY4MDc0MGQ2MThhN2MxMTEwMjM0MDdfMjlhMWMxNjhjMTJjZDdlYjgxMzRjZWQ5NDBiZmI2NTBfSUQ6NzY3MTEyOTE3MjEwNTk4OTMzMF8xNzg3MDE0OTQ4OjE3ODcxMDEzNDhfVjM)

虽然不是严格意义的 “均匀”，但是差异非常小

此时这三个分片上的数据就是比较均匀的了

这种算法，本质上就是把 一致性哈希 和 哈希求余 这两种方式结合一下

**上面这只是一种可能的分片方式，实际上分片是非常灵活的，每个分片持有的槽位号，可以是连续的也可以是不连续的**

此时，每个分片都会使用 “位图” 这样的数据结构，表示出当前有多少槽位号

**16384 个 bit 位（2048\-\>2KB），用每一位 0/1 来区分自己这个分片是否持有该槽位号**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjI5Y2M2OTE2MDZjNjEyYTlhMGQ0ZGY3NTI0OGEzMWJfNWMwNmE5ODNkZWI5ZjczMDI0ZDkwOWIxZDVmMjAyZDdfSUQ6NzY3MTEzMDYxNjI2ODM3NzM2Ml8xNzg3MDE0OTQ4OjE3ODcxMDEzNDhfVjM)

针对某个分片，上面的槽位号不一定非得是连续的区间，毕竟是使用的位图嘛

**这个新的分片和原有的分片现在也是均衡的，也不会数据倾斜；在上述过程中，只有被移动的槽位，对应的数据才需要搬运**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ODU2MjgzMWNlZDYxYTI0ZjRhMzRlNDcwYjY4MDlhYThfZDVmNTViY2ZmMGIyMTVmNTYxMWI4OGYzN2Q1NjhlODlfSUQ6NzY3MTEzMTEwMTAyMDYwNTY2Ml8xNzg3MDE0OTQ4OjE3ODcxMDEzNDhfVjM)

在 redis 中，当前某个分片包含哪些槽位，都是可以手动配置的

### **此处还有两个问题【经典面试题】**

1. **Redis 集群是最多有 16384 个分片嘛**

    - 如果这样的话，那就是每个分片上只有一个槽位，key 是要先映射到槽位，再映射到分片的，如果每个分片包含的槽位比较多，如果槽位个数相当，就可以认为是包含的 key 数量相当的，如果每个分片包含的槽位非常啥，槽位个数不一定能直观的反应到 key 的数目

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YjI5OTk4ZDA3ZWIyZTQxMjZkYTNhN2U1ZjcwYTUwMDBfYTBmZWVhYjMyNjExYmNkM2FmMzYyZGNmYmQyZmJmMjFfSUQ6NzY3MTEzMjAwNDU1ODkwMDE3NV8xNzg3MDE0OTQ4OjE3ODcxMDEzNDhfVjM)

实际上 Redis 的作者建议集群分片数不应该超过 1000，而且如果真是 1\.6w 个分片，整个数据服务器的集群规模就太可怕了，几万台主机构成的集群，整个集群的可用性是非常堪忧的

2. **为什么是 16384 个槽位？**
