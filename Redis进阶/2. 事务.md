# 一\. 认识 Redis 事务

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MTQ5ZmViMTRkYzk2ZGEwMjkzY2VhOGE3ZjEyOWRmNjJfNWZlY2VlMjdiMThmNTNhMzUyNmRiZmM4YmU2Y2NmMjFfSUQ6NzY2NzQ5MzQ2ODA4ODE1OTE2MV8xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)

Redis 的事务和 MYSQL 一比，那就是个弟弟

- 弱化的原子性：redis 的事务到底有没有原子性，存在争议

最原本的含义，是把多个操作打包到一起，要么全都执行（但是不保证成功，如果若干个操作，存在有失败的，那就失败呗，不会有回滚操作），要么全部不执行，原子就是不可拆分的最小单位

Redis 做到了上述的含义，但是 MYSQL 这里的原子性，走的更远，也是把多个操作打包到一起，要么全都执行成功（如果事务中有操作执行失败，要进行回滚，把中间已经执行的操作，全部回退了），要么全都不执行

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NjBmZTg2OTBmODg1NmQxMWU5NzBlZmFhMjdkMTJjMzdfNjI2ODhhYTU0YmU0ZjljODg4M2QyNjlmZDdhNzRmNjVfSUQ6NzY2NzgyNDYxNzgzNTEyMTk1NF8xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)

但是 redis 的这个已经可以称之为原子性了，但是 MYSQL 标杆，提高了 “原子性” 的门槛，这就使人们谈到原子性的时候，更多的是想到的 MYSQL 这种带有回滚的原子性

网上看到，有人说，redis 事务有原子性（只是打包一起执行），有的说没有原子性（打包一起执行 \+ 带有回滚机制，也就是打包一起正确执行）

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzM1N2M0NzBlZDAzODNhMDQzYTYwZDg5NzE1ZGQ4ZjBfZmY1OGVjMjRiZDVlMzYyODk0ZDQzNTdhZTQ3MDJhMTRfSUQ6NzY2NzgyNTcxNjI5NzkxMTU5OF8xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)



- 不具备一致性：redis 没有约束，也没有回滚机制，事务执行过程中如果某个修改操作出现失败，就可能引起不一致的情况

- 不具备持久性：redis 本身就是内存数据库，数据是存储在内存中的，虽然 redis 也有持久化机制，但是这里的持久化机制和事务没有啥直接关系

- 不涉及隔离性：redis 是一个单线程模型的服务器程序，所有的请求/事务，都是 “串行” 执行的



Redis 的事务，主要的意义，就是为了 “打包”，避免其他客户端的命令插队插到中间



Redis 中实现事务，是引入了队列（每个客户端都有一个），开启事务的时候，此时客户端输入的命令，就会发给服务器并且进入这个队列中（而不是立即执行）

当遇到了 “执行事务” 命令的时候，此时就会把队列中的这些任务都按照顺序依次执行

Redis 主线程中完成的（主线程会把事务中的操作都执行完，再处理别的客户端）



Redis 的事务为啥就搞的这么简单，为啥不设计成和 MYSQL 一样强大呢

MYSQL 的事务，在背后付出了很大的代价，空间上，要花费更多的空间来存储更多的数据，时间上，也要有更大的执行开销

正是因为 MYSQL 上述的问题，才有了 redis 上场的机会

啥时候需要使用到 Redis 的事务呢

如果我们需要把多个操作打包进行，使用事务是比较合适的

# 三\. WATCH 的实现原理

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjQxNmZhYzNlZWEwYTUwNTA0NzliNTAyYzc5OWYxYjhfMGVkN2RhMTI2NzhkYzExYjhmNDFmMmM2ZjZmYzgxNmNfSUQ6NzY2ODIzODk2ODM2MjIyNDYxOF8xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NGU5MDM5N2VmZjMzMDY4ZGM1ZjliNjkyNGQ0MDk4YTVfZmZiY2EzY2Y5YmU1Y2U2YTkxM2U2M2VhN2YxYTY2MGJfSUQ6NzY2ODI0MDA2NTEzMDY3OTU4N18xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)

从时间上来看，客户端1 是先发送了 set key 222，客户端2 是后发送了 set key 333

由于 客户端1，得是 exec 执行了，才会真正执行 set key 222，这个操作就变成了实际上更晚执行的操作，最终值就是 222

但是这样的规则，容易产生歧义，这个场景中，我们就可以使用 watch 命令来监控这个 key，看看这个 key 在事务的 multi 和 exec 之间，set key 之后，是否在外部被其他客户端修改了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZGE2ZDc1OTU2MTZmOTgzY2FmMTE3YjI4YmEyODg4ZTZfOTk4YTU5OTg1MTY4Nzk2ZTRmNzIyMjUzMDkzZmU0MWJfSUQ6NzY2ODI0MTExMzk4ODk1OTE4M18xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)

此时，exec 在执行上述事务的命令的时候，发现 key 在外部有修改，于是真正执行 set key 222 的时候就报错了就没有真正执行

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjE2OWY3NjViMWEyMDVmOWVlMTRiZmYwM2FkMzg4M2RfMDdjZDljYTc4NDgyZTkyZWIxZTA0N2JlZDE0YTlkOTNfSUQ6NzY2ODI0MTgzOTE0NDc4MzA1MV8xNzg1NTU0MDA1OjE3ODU2NDA0MDVfVjM)

是另外一个地方修改的 333



这个 watch 的实现，类似于一个 “乐观锁”

乐观锁，悲观锁，不是指某个具体的锁，而是指的某一类锁的特性

- **乐观锁**：加锁之前，就有一个心里预期，预期接下来锁冲突的概念比较低

- **悲观锁**：加锁之前，也有一个心里预期，接下来锁冲突的概率比较高

# 四\. 事务小结

Redis 的事务，要比 mysql 的事务，简单很多

1. 原子性：Redis 的事务，并不支持回滚

2. 一致性：Redis 并不会保证事务执行前和执行后，内容统一

3. 持久性：Redis 主要通过内存来存储数据，redis 的持久化操作和事务是没关系的，而且可以自己关掉

4. 隔离性：Redis 自身作为一个单线程的服务器模型，上面处理请求本质上都是串行执行的
