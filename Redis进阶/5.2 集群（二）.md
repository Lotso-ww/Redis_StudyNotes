# 二\. 故障处理

使用集群之后，之前学过的命令，都能正常使用（不够严谨）

因为有些指令，是能够操作多个 key 的

此时如果 key 是分散在不同的分片上，就可能出现问题了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MGM3MGM1YzBiZjJjNWZmMDZmNDExYjlmZWRiMGUzMjVfNDlkMmMwZjM3ZDdlYTYxYjhmOTRmYjFiZTNhM2NkNzdfSUQ6NzY3MjMyNjkxOTg4NzczNTc2NF8xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

其实也是有特殊的方式，解决上述问题的（hash tag）

如果集群中有节点挂了呢？

1. 如果挂了的节点是从节点，没事

2. 如果挂了的节点是主节点

主节点才能处理写操作，从节点是不能写的

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YzVjNmI2NzVjODFkMTEwZTYwYWViZWRlZjEyZmU2YWNfZDNhM2FiNTcxYWE2MDk0ZGMyMDVhYWY2OTVlNDQ2MmVfSUQ6NzY3MjY2NjE0NDEyMTU1NjIwM18xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

当尝试在从节点上写操作，此时就会自动的被重定向到指定的主节点上



![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=Y2I2ZjJjNWZkOWVhNTE1NGQ2MGVmNWU1ZTM1Y2E1Y2VfMzJhMGZhYmVhYWM5MTM4YWI0NzlmM2IyMzAxMmY0N2JfSUQ6NzY3MjY3MzMxNTMwODE2MjAyN18xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

我们把 redis1 给停掉

此处，集群做的工作，就和之前哨兵做的类似了，如果主节点挂了就会自动的把该主节点下从节点，给挑出来一个，提拔成主节点

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MjkyM2ZlMzgzMDdmMDk4MjQ1MmUyMzQxZDU1ODhmZDFfNDM2ZWMyZDg5YTM2Y2VjMDNiODZjYzRlNTA3MTc2MzRfSUQ6NzY3MjY2NzAzNjYxOTAwMDc2Ml8xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

之前的时候，101 是主节点，105 和 106 是从节点，当 101 挂了之后，106 成了新的主节点，代替了原来 101 的位置，与此同时，105 就成了 106 的从节点了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=Y2UzYzNjOWFiNjU4YjlkMTVhZWZjYjg3NWEyN2EyOWVfMTc0MGIyYTdkOWFjOWIzOTMxZDlmOWE1NzMwYzYzOTVfSUQ6NzY3MjY2NzYyNzMxNTQ0ODc2M18xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

集群机制，也能处理故障转移，但是此处故障转移的具体处理流程和哨兵这块的处理流程还不太一样

1. 故障判定：识别出某个节点是否是挂了

肯定是心跳包，具体流程如下：

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YjZjN2MyODVhMjY5ZTc0YmNjNTg0NjM5ZDFjM2ZiZjNfMThlMDViN2RkMjg2OTVlMDVmMzgyYWI0MWUzZGMzM2FfSUQ6NzY3MjY2OTI3Mzk1OTc5NTY2M18xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

此时 B 是否下线就可以通过上述流程明确了

2. 故障的迁移

    - 如果 B 是从节点，那么就不需要进行故障迁移

    - 如果 B 是主节点，那么就会由 B 的从节点（比如 C 和 D）触发故障迁移了

具体步骤如下：

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZGMzMzk0NjNkYzAyNTA1ZGE1OTk1MWNlYjBjMGE1MTBfMzJlZTBhNDgwYTVhYTM1YTIxMWQzMGMyZjc4MGI0ODlfSUQ6NzY3MjY3MTI4MjM5OTU0NjU1M18xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

哨兵是先竞选出 leader，leader 负责找一个从节点升级成为主节点，这里是直接投票选出新的主节点

> 上述选举的过程，称为** Raft 算法**，是一种在分布式系统中广泛使用的算法，在随机休眠时间的加持下，基本上就是谁先唤醒，谁就能竞选成功
> 
> 

更多的时候是为了选一个节点出来，至于选谁，没那么重要

网上谈到 redis 的选举，大部分的资料都是关于 哨兵 中选 leader 的，谈到集群中选新 master，资料比较少【质量也相对比较差】



以下三种情况会出现集群宕机：

1. 某个分片，所有的主节点和从节点都挂了

2. 某个分片，主节点挂了，但是没有从节点

3. 超过半数的 master 节点都挂了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MWVhNDAyMGM5NWI2MGZkYWUwZTZiNzBkNDIzMTUzYzZfMjBhZThiYjdmNDAxYzExYzU4OGU0MTMxYTBjMjExOGFfSUQ6NzY3MjY4NDc2NDgyNjQyMjQ4N18xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

如果集群中有个节点挂了，无论是什么节点，程序员都需要尽快的处理好

把之前三组 master 上面的 slots 拎出来一些，分配给新的 master

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=N2I1MTE3YTkzMDBmZWQ1ZWE0ZGYwYTkyOTBkYzNjYTBfZjVmMmMxN2NiZGNjMzNiMGNmNDU5ODA1OTljYWZiZjhfSUQ6NzY3MzQyMTk3Mjc5NzU5MDQ1OV8xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

紧接着会询问让哪个节点来接受，我们就复制一下110这个节点的ID

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzU5ZWYyZThmY2M3NzYwYmRkMGQ0NzcxMDk2MTVmMjRfMTA4YTdiOTljYTU3ODgwYTIyZWJhZjMxMDlmODIyN2NfSUQ6NzY3MzQyMjMyMDIzMjk5MTY4Nl8xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

输入从哪些节点来移动 slots

- all，表示从其他每个持有 slots 的 master 都拿过来点

- 手动指定，从某一个或者某几个节点来移动 slots（以 done 为结尾）

我们直接输入 all，会给出一个搬运的计划（还没真正搬运）

当我们输入 yes 之后，搬运真正开始，此时不仅仅是 slots 重新划分，也会把 slots 上对应的数据，也搬运到新的主机上（这是一个比较重量的操作）

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MmVmNjY2N2VlMmVjZTQ2NzI1MzYwZDhiNDg0ZTM4ZWJfMDczYTM5ZTNiYjJmNzRhOGY1N2Y1ODIyZTI5NzUzZGJfSUQ6NzY3MzQyNDgxOTYxNDg0NTkyMV8xNzg3MjE5OTMzOjE3ODczMDYzMzNfVjM)

如果在搬运 slots / key 的过程中，此时客户端能否访问咱们的 redis 集群呢

搬运 key，大部分的 key 是不用搬运的，针对这些未搬运的 key，此时是可以正常访问的，针对这些真正搬运中的 key，是有可能出现访问出错的情况

假设，客户端访问 k1，集群通过分片算法，得到 k1 是第一个分片的数据，就会**重定向到第一个分片的节点，就可能在重定向过去之后，正好 k1 被搬走了，自然就无法访问了**

如果想针对生产环境进行扩容操作，还是悠着点，比如，找个夜深人静，没啥客户端访问集群的时候，进行扩容，就可以把损失降到最低

很明显，要想追求更高的可用性，让扩容对应用户影响更小，就需要搞一组新的机器，重新搭建集群，并且把数据导入过来，使用新集群代替旧集群（成本最高的）
