在分布式系统中，是有很多进程的（每个服务器都是独立的进程）

因此，之前的锁，就难以对现在分布式系统中的多个进程之间产生制约

分布式系统中，多个进程之间的执行顺序也是不确定的 \-\> 随机性

**引入 “分布式锁” 来解决上述问题**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NmFlOWUxYjg5YTEyNzVhMDljYWI2YTg4YmJiZjJhMTZfZTRjODM4NmQ0YzFkZGI0OWQwNjE3ZmZmNzM5MGE3ZGZfSUQ6NzY3NDkyMTUyMzQ2Mzc1Mjk3MF8xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

先查询指定车次的余票，如果余票 \> 0，则设置余票值 \-= 1

如果：

- 客户端1 先执行查询余票，发现剩余 1 张，在即将执行 1\-\>0 过程之前

- 客户端2 也执行查询余票，发现也是剩余 1 张，客户端2 也会执行 1\-\>0 过程

这就造成了超卖 \-\> 一张票，卖给两个人

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzIxMjc0NDQ4NTAwOWM4NmQ3YzJlYjY2Y2YxMjMxYTlfMTYwNDlhNTYxZjRiMTZlNzZkNTYzYWVkOGJmM2Q4NjVfSUQ6NzY3NDkyNzk4NTU3NzM0ODMzMV8xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

所谓的分布式锁，也是一个/一组 单独的服务器程序，给其他的服务器提供 "加锁" 这样的服务（Redis 是一种典型的可以用来实现分布式锁的方案，但是不是唯一的一种，业界可能也会使用 mysql/zookeeper 这样的组件来实现分布式锁的效果）

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NjI1ZTYzZmUyYjQ0NjA1Mjc4NDVmNTEwOTg2MjJjZjRfMDY3NWE2MDBlOTU0ZTIxZGEwYzZjMjUzNDYxM2I5NDlfSUQ6NzY3NDkyODU0MzYyMDU4MjM4M18xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

买票服务器，在进行买票操作的过程中，就需要先加锁

往 redis 上设置一个特殊的 key \- value，完成上述买票擦走，再把这个 key \- value 删除掉

其他服务器也想买票的时候，也去 redis 上尝试设置 key \- value，如果发现 key \- value 已经存在，就认为 “加锁失败”，（是放弃/阻塞，就看具体的实现策略了）

就可以保证第一个服务器执行 “查询 \-\> 更新” 过程中，第二个服务器不会执行 “查询”，也就解决了上述 “超卖” 问题

**刚才买票的场景，使用 mysql 的事务，也可以批量执行 查询 \+ 修改 操作，但是分布式系统中，要访问的共享资源，不一定是 mysql\.\.\.\.，也可能是其他的存储介质，没有事务，也可能是执行一段特定的操作，是通过统一的服务器来完成执行动作**

# 二\. 分布式锁

## 2\.1 引入 setnx

不存在就设置，存在就出错

使用 setnx 确实可以得到 “加锁” 效果，针对解锁，就可以使用 del 命令来完成 \-\> 某个服务器，加锁成功了（setnx 成功），执行后续逻辑过程中，程序崩溃了，没有执行到解锁

之前讲过，为了保证解锁操作能够执行到

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZmY0ODg5YzM2NTMwZjVkNDA5MTY4YTViNGRjOTIxOWFfZDdmMGNmZjA5NmU0YTYwZTE2YWM2MzhhZjkxZGMzMmJfSUQ6NzY3NTIwOTgyNDc4Mjc4MTYzMF8xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

在分布式系统上述的做法无效，上面的只针对进程内的锁有用（进程退出锁也会销毁的），针对分布式锁无效

**比如，服务器直接掉电，进程直接异常终止 \-\> 这样的情况就会导致 redis 上设置的 key 无人删除，也就导致其他服务器无法获取到锁了**

## 2\.2 引入过期时间

我们可以给 set 的 key 设置过期时间的，一旦时间到，key 就会自动删除掉了

set ex nx 这样的命令来完成设置

**比如，设置 key 的过期时间，为 1000ms，那么意味着即使出现极端情况，某个服务器挂了，没有正确释放锁，这个锁最多保持 1000ms，也就会自动释放了**

## 2\.3 引入检验id

- 所谓的加锁，就是给 redis 上设置一个 key\-value

- 所谓的解锁，就是给 redis 上这个 key\-value 删除

是否可能会出现，服务器1，执行了加锁，服务器2 执行了解锁？

正常来说，肯定不是故意的，但是代码总会有 bug

不小心就执行到了解锁操作，因此就可能进一步的给整个系统带来更严重的问题（比如像超卖）

**为了解决上述问题，就需要引入一点校验机制**

1. 给服务器编号，每个服务器有一个自己的身份标识

2. 进行加锁的时候，设置 key\-value 对应着要针对那个资源加锁（比如车次），value 就可以存储刚才服务器的编号，标识出当前这个锁是那个服务器加上的

后续在解锁的是就可以进行校验了

**解锁的时候，先查询一下这个锁对应的服务器编号，然后判定一下这个编号是否就是当前执行解锁的服务器编号，如果是，才能真正执行 del，如果不是，就失败**

这个是服务器这边要完成的逻辑，通过上述校验，就可以有效避免 “误解锁”

上述服务器，就是咱们自己写的代码，初心是为了避免误会，不会说服务器故意搞破坏的

## 2\.5 引入看门狗

我们还需要考虑过期时间的续约问题

我们之前说要在加锁的时候，给 key 设定 过期时间

**过期时间，设置多少合适？**

- 如果设置的太短，就可能在你的 业务逻辑 还没执行完，就释放锁了

- 如果设置的太长，就会导致 “锁释放不及时” 问题

**更好的方式，是 “动态续约”（往往也需要服务器这边有一个专门的线程，负责续约这个事情）****我们把这个负责的线程，叫做 “看门狗”（watch dog），这也是一个比较广义的概念，很多场景都会涉及到这种针对过期时间的操作，很多时候就会引入 “看门狗”**

**初始情况下，设置一个过期时间（比如设置1s）就提前在还剩300ms的时候（也不一定就是 300ms，数值都灵活调整），如果当前任务还没执行完，就把过期时间再续上1s，等到时间又快到了，任务还没执行完，就再续（无限续杯）**

**如果服务器中途崩溃了，自然就没人负责续约了，此时锁就能在较短的时间内被自动释放**

## 2\.6 redlock 算法

使用 redis 作为分布式锁，redis 本身有没有可能挂了呢，这个是非常可能的

要想保证 “高可用” 就需要通过这样一系列的 “预案演习” 

主从复制，哨兵，集群

我们选择哨兵，集群更多的是解决存储空间不足问题

分布式锁场景中，涉及到的数据量不大

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ODY3MTcyYmMzNzhmZWQxODY2ZTVmM2NkNjYzMDhiZTFfZTFhZmM1ZjJhNTQwNjQ2YjllNThkZGQ3ZjBlNWFlODVfSUQ6NzY3NTI1NzE1NjUzMDY3MDg1MV8xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=YjgwMTU3MTk3NjYwODViMTM3YjQ2YTc0YTZjYmM3OWFfYjA4ZGU5MjkzMGQyOWRjMDU0ODgxMzY5NzcwYTI3OWZfSUQ6NzY3NTI1NzI5MDMxNjY5Njc1NV8xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

**进行加锁，就是把 key 设置到主节点上，如果主节点挂了，有哨兵自动的把从节点升级成主节点，进一步的保证刚才的锁仍然可用**

**主节点和从节点之间的数据同步，是存在延时的！可能主节点收到了 set 请求，还没来得及同步给从节点呢，主节点就先挂了，即使从节点升级成了主节点，但是刚才的加锁对应的数据，也是不存在的**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjdhZWE2ZDRlOTRhZmExNjY3MDdmOTM2MjhhY2YzMjFfOGJiMWU2YTIzYTZmZGZhMmQzOWM2Y2E2NmFmNWRiOWZfSUQ6NzY3NTI1NzgxOTkwNjI0Nzg5M18xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

**作为分布式系统，就需要随时考虑某个节点挂了的情况，需要保证某个节点挂不会影响到大局**

**redlock 算法（redis 作者给出的一个方案），其实就是冗余**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MWIwNjM3OTA0MzEwYmVlN2M4ZTNjM2JjY2YxZWU5NWRfNjQ1MWI3MDJkMTc2YTVhYTFlNTVhMmE2YmYzYjcyYmJfSUQ6NzY3NTI1ODcwMzgyNTkzMTIwNF8xNzg3NDAyNzg1OjE3ODc0ODkxODVfVjM)

此处加锁，就是按照一定的顺序，针对这些组 redis 都进行加锁操作

如果某个节点挂了（某个节点加不上锁，没关系，可能是 redis 挂了）

继续给下一个节点加锁即可，如果写入 key 成功的节点个数超过总数的一半，就视为加锁成功

同理，进行解锁的时候，也就会把上述节点都设置一遍解锁
