# 二\. 使用 Redis 作为缓存

通常是使用 redis 作为数据库的缓存（mysql）

数据库是一个非常重要的组件，绝大部分商业项目中都会涉及到，并且 mysql 的速度又比较慢，使用 redis 可以作为 mysql 的缓存

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NWVhYmI1YWU0ZGZiODFmNjE0MjUxODMyYjhjMTY2ZDVfNWZhMjhlZTk3OTA2MTg0ZjAzN2UyYWQ5ZmYwM2NhNTNfSUQ6NzY3NDUyNjQ1OTM2NDQxMjU5NV8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

因为 mysql 等数据库，效率比较低，所以承担的并发量就有限，一旦请求数量多了，数据库的压力就会很大，甚至很容易就宕机了

服务器每次处理一个请求，一定都要消耗一些硬件资源（CPU，内存，硬盘，网络）任意一种资源的消耗超出了机器能提供的上限，机器就很容器出现故障了

# 三\. 缓存更新策略

如何知道 redis 中应该存储哪些数据？如果知道哪些数据是热点数据呢？

## 3\.1 定期生成

会把访问的数据，以日志的形式记录下来

比如搜索引擎，“查询词” （搜索引擎，搜索框里面输入的词）就是要关注的 “访问数据”

我们通过日志，把都使用了哪些词，给记录下来，就可以针对这些日志进行统计，统计这一天，每个词出现的频率，再根据频率降序排序，再取出前20%的词，就可以把这些词认为是 “热点词”

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZTQ1ZTYzZmZmZjVhZTgxYTRjMzU3OTEyMjIzZmRjZmNfNWNlZGExMDAzMzM0MmY2MWIyYjVhZDJmYWIzZDU0MjBfSUQ6NzY3NDgxNzIwNzY2NzI5NzQ5Ml8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

接下来就可以把这些热点词，涉及到的搜索结构，提前拎出来，就可以放到类似于 “redis” 这样的缓存中了

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MDg3ODg3MDk3NmYzM2E3MDQzZTIyMTkyZGEyMzYxODFfOWFkOGEyYjM5ZWMwM2VlZmM3Mzc1OWZhYzZkMGYyYTBfSUQ6NzY3NDgxNzYxMTgyMTEwODE3Nl8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

此处的数据，就可以根据当前这里统计的维度，来定期更新

按照天级别统计，就每天更新一次

按照月级别统计，就每个月更新一次

我们可以写一套离线的流程（往往使用 shell，Python写脚本代码）可以通过 定时任务 来触发

- 完成统计热词的过程

- 根据热词，找到搜索结果的数据（广告数据）

- 把得到缓存数据同步到缓存服务器上

- 控制这些缓存服务器自动重启

**优点**：上述过程，实际上实现起来是比较简单的，过程更可控（缓存中有啥事比较固定的），方便排查问题

**缺点**：实时性不够，如果出现一些突发性事件，有一些本来不是热词的内容，成了热词了，新的热词就可能给后面的数据库啥的带来较大的压力

## 4\.1 缓存预热

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MmJlNWViZjM2YTgwNDViODUxOTVkNmJmNjM1NjFiYTdfZmIwMzEwZjNmMWRiYmRlNmNlMTFiMjExOTY4NTIyMzhfSUQ6NzY3NDgzMTk3MjcxMTg3NzYwNl8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=N2YzZjc4MDY2NTE5ZjhiNWY4YTM0MzZhZGY4ZGFmZjJfYjRjYmMwNWE2YTM3MzE3YmVlMWY2Yjk1NjRkMjJhY2RfSUQ6NzY3NDgyOTUxNjgxMjI3NDY2MV8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

客户端先查询 redis，如果没查到，就再查一次 mysql，查到了之后，会把数据也写入到 redis 中

**Redis 服务器首次接入之后，服务器里是没有数据的****（此时，所有的请求都会打给 mysql，要随着时间的推移，redis 上的数据就越积累越多，mysql 承担的压力就逐渐减小了）**

**缓存预热就是用来解决上面的问题的**

**把 定期生成 和 实时生成，结合一下，先通过离线的方式，通过一些统计的途径，先把热点数据找到一批，导入到 redis 中，此时导入的这批热点数据，就能帮 mysql 承担很大的压力了，随着时间的推移，逐渐就使用新的热点数据淘汰掉旧的数据**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzhhYmQ0YTdhMjdiMjVmNWVmNWVjYjhjMTI2MDQyMzlfMTNkMjJlMjdlMTQ1NTAzZjM3NzZiMzRiMTQ2N2VmOGZfSUQ6NzY3NDgzMDk2Mzk1NjA0MjY4Ml8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

## 4\.2 缓存穿透

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=Y2MzM2RmZjMwYzcwYjVmOWE5ODY2YWY5YTMzNjIxMDlfYzU4ZTFmNzU1YzA4OTcwNjYwYTc3NjZmMjc3OTU4ZWFfSUQ6NzY3NDgzMjAyMTczNTEzMjA5N18xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

当前查询的某个 key，在 redis 中没有，mysql 中也没有，这个 key 肯定也不会被更新到 redis 中

**这次查询，没有，下次查也肯定是没有的\.\.\.\.**

**如果像这样的数据，存在很多，并且还反复查询，一样也会给 mysql 带来很大的压力**

**为什么会产生：**

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjliYmU1YjM0NzEzZTMzOTc2ODFiMmEyNzI5NjIyNTFfOWNjMWQzNTIxNzFlOTVkNDk2OGUzMzYyMjY3ZjM2MTRfSUQ6NzY3NDgzMjY5MjUzMzUyOTc3OF8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

**如何解决**：

通过改进业务/加强监控报警都是属于亡羊补牢，发生了之后再去解决，我们还有更靠谱的方案：

1. 如果发现这个 key，在 redis 和 mysql 上都不存在，仍然写入 redis 中，value 设成一个非法值（比如 “”），降低问题的严重性

2. 还可以引入 布隆过滤器，每次查询 redis/mysql 之前都先判定一下 key 是否在 布隆过滤器 上存在（把所有的 key 都插入到 布隆过滤器中），布隆过滤器本质上是结合了 hash \+ bitmap，以比较小的空间开销，比较快的时间速度，实现针对 key 是否存在的判定

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MGQ5MzY2YmNiN2RiYzhhZTRmYWM5YmEyMzNhNmU5ZjRfMjMxMWRjYTI2ZGQyM2MxNjc2YjVhOTgzNWM5MzM2N2NfSUQ6NzY3NDgzNDM5NTQ3NjAwNDEwNV8xNzg3MjczMDQ1OjE3ODczNTk0NDVfVjM)

## 4\.3 缓存雪崩

由于在短时间内，redis 上大规模的 key 失效，导致缓存命中率陡然下降，并且 mysql 的压力迅速上升，甚至直接宕机

1. Redis 直接挂了，redis 宕机 / redis 集群模式下大量节点宕机（这个可以使用之前的集群或者哨兵进行解决）

2. Redis 好着呢，但是可能之前短时间内设置了很多 key 给 redis，并且设置的过期时间是想通过的

给 redis 里设置 key 作为缓存的时候，有的时候为了考虑缓存的时效性，就会设置过期时间（和 redis 内存淘汰机制是配合使用的）

**解决方案**：

- 加强监控报警，加强 redis 集群可用性的保证

- 不给 key 设置过期时间 / 设置过期时间的时候添加随机的因子（避免同一时刻过期）

## 4\.4 缓存击穿

其实叫做缓存瘫痪是更合适的，这个就是一个翻译的问题了，但是我们现在也还是都叫做缓存击穿的

相当于缓存雪崩的特殊情况，针对热点 key，突然过期了，导致大量的请求直接访问到数据库上，甚至引起数据库宕机

热点 key 访问频率高，影响肯定是更大的

**基于统计的方式发现热点 key，并设置永不过期****（往往需要服务器结构做出较大的调整，没这么好实现）**

**进行必要的服务降级，例如访问数据库的时候使用分布式锁，限制同时请求数据库的并发数****（本身服务器的功能，有 十个，但是在特定情况下，适当的关闭一些不重要的功能，只保留核心功能（服务降级）\-\> 省电模式）****通过分布式锁，限制数据库的访问频率**
